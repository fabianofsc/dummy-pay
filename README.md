# DummyPay

A self-contained, deterministic card PSP for testing payment integrations.
It speaks a real-shaped HTTP API, keeps its own PostgreSQL database, and never
accepts card data.

## What it does

DummyPay exposes one payment operation — **sale**: authorize and capture in a
single call. There is no separate capture step.

The outcome of a payment is chosen by the caller through an opaque **scenario
token**, so every test is reproducible:

| Token                       | Behaviour                          |
| --------------------------- | ---------------------------------- |
| `card_approved`             | `APPROVED` immediately             |
| `card_declined`             | `REJECTED` immediately             |
| `card_processing_approved`  | `PROCESSING`, then `APPROVED`      |
| `card_processing_declined`  | `PROCESSING`, then `REJECTED`      |

The delay before a `PROCESSING` payment settles is configured per environment
and is zero (or driven by a controllable clock) in tests.

## Core concepts

**Technical account.** Exactly one per environment, provisioned from
configuration. It owns every payment and the webhook subscription. There is no
multi-tenancy in V1.

**Payment.** A single sale. Identified by a stable `payment_id` generated by
DummyPay, plus a `provider_transaction_id` representing the transaction on the
(imaginary) acquirer side. Both are stable for the life of the payment.

**Identifiers.** Every public identifier is a UUIDv7 with a type prefix:
`pay_`, `txn_`, `sub_`, `evt_`, `dlv_`. The prefix exists to make identifiers
self-describing in logs; it is not part of the stored value. Treat identifiers
as opaque strings.

**Payment status.** One of `APPROVED`, `REJECTED`, `PROCESSING`. `PROCESSING`
is transient and always resolves to `APPROVED` or `REJECTED`.

**Reference ID.** An opaque string supplied by the caller (e.g.
`checkout:123`). DummyPay stores and echoes it and gives it no meaning.

**Idempotency key.** A caller-supplied header that makes payment creation safe
to retry. See [POST /v1/payments](#post-v1payments).

**Webhook subscription.** Registered once, up front. Callback URLs are *not*
attached to individual payments. One active subscription per technical account
in V1.

**Webhook delivery.** One attempt-tracked record per event sent to the
subscription. Persisted before it is sent.

## Stack

| Concern | Choice | Why | ADR |
| --- | --- | --- | --- |
| Language | Go | — | — |
| Architecture | Lean hexagonal | `internal/payment` holds the domain and use cases and imports no infrastructure. `internal/http`, `internal/postgres`, and `internal/webhook` are adapters behind ports the domain declares, so the rules are testable in memory. | [0003](docs/decisions/adr-0003-lean-hexagonal-architecture.md) |
| Database | PostgreSQL via `pgx/v5`, hand-written SQL | Idempotency and worker claiming are database guarantees — `INSERT … ON CONFLICT` and `FOR UPDATE SKIP LOCKED`. An ORM would hide precisely what has to be reviewable. | [0004](docs/decisions/adr-0004-postgresql-pgx-hand-written-sql.md) |
| Router | `chi` v5 | Handlers stay `http.HandlerFunc`, so `httptest` needs no adapter and no framework context reaches the domain. Route groups apply auth to `/v1` as a unit instead of per handler. | [0005](docs/decisions/adr-0005-chi-http-router.md) |
| Identifiers | UUIDv7 in native `uuid` columns, prefixed at the boundary | Time-ordered, so inserts keep index locality and `ORDER BY id` is chronological, without UUIDv4's fragmentation. | [0006](docs/decisions/adr-0006-uuidv7-identifiers.md) |
| Idempotency | Unique constraint plus an explicit `IN_FLIGHT`/`COMPLETED` state | The race is settled by the database, so the guarantee holds across processes. 409 versus replay is recorded state, not inference. | [0007](docs/decisions/adr-0007-idempotency-unique-constraint.md) |
| Async work | Outbox table plus an in-process worker | Settlements and deliveries are rows with a due time, written in the same transaction as the change that caused them. Survives restart; `retry` re-enqueues. | [0008](docs/decisions/adr-0008-outbox-in-process-worker.md) |
| Secret at rest | AES-256-GCM under a key separate from the database DSN | Signing must be reversible, so hashing is unavailable. A leaked DSN alone cannot forge events. | [0009](docs/decisions/adr-0009-webhook-secret-encryption.md) |
| Configuration | Environment variables only | No config file is read, so no secret can be committed by accident. | [0010](docs/decisions/adr-0010-configuration-from-environment.md) |
| Migrations | `goose`, embedded via `embed.FS`, applied at startup | Schema and binary ship together and cannot drift. Clone and run needs no extra tool. | [0011](docs/decisions/adr-0011-embedded-goose-migrations.md) |
| Determinism | Injected `Clock`; schedule expressed as `due_at` data, not timers | Real delay in development, zero in tests, with no `time.Sleep` anywhere in the suite. | [0012](docs/decisions/adr-0012-injected-clock-scheduler.md) |
| Test database | PostgreSQL from `docker compose`, one schema per test | The semantics tested are the semantics shipped. Pulled once, offline thereafter. | [0013](docs/decisions/adr-0013-integration-tests-real-postgres.md) |

Full reasoning for each, including the options rejected and what each choice
costs, is in **[docs/decisions/](docs/decisions/)**. Read those before proposing
a change to the stack — several of these were close calls and the arguments are
recorded so they don't have to be had twice.

## API

All endpoints are JSON over HTTP under `/v1`. Requests and responses use
`application/json`.

### Authentication

Every endpoint requires HTTP Basic authentication with the technical account's
credentials, which come from the environment:

```
Authorization: Basic <base64(key_id:key_secret)>
```

Missing or invalid credentials return `401`.

### POST /v1/payments

Creates and settles a sale.

**Headers**

| Header            | Required | Notes                        |
| ----------------- | -------- | ---------------------------- |
| `Authorization`   | yes      | Basic, technical account     |
| `Idempotency-Key` | yes      | Non-empty string             |
| `Content-Type`    | yes      | `application/json`           |

**Request**

```json
{
  "reference_id": "checkout:123",
  "amount": 10990,
  "currency": "BRL",
  "payment_token": "card_processing_approved"
}
```

| Field           | Type    | Rules                                          |
| --------------- | ------- | ---------------------------------------------- |
| `reference_id`  | string  | Opaque, caller-defined                         |
| `amount`        | integer | Positive, in cents (`10990` = R$ 109,90)       |
| `currency`      | string  | `BRL` only                                     |
| `payment_token` | string  | One of the four scenario tokens above          |

**Response — `201 Created`**

```json
{
  "payment_id": "pay_0199a1f4-3c82-7d19-b4e6-2f8a91c05d3b",
  "provider_transaction_id": "txn_0199a1f4-3c83-7a04-8f21-6d3b0e57c91a",
  "reference_id": "checkout:123",
  "amount": 10990,
  "currency": "BRL",
  "status": "PROCESSING",
  "created_at": "2026-08-10T12:00:00Z"
}
```

**Idempotency rules**

- Replaying the same `Idempotency-Key` with the **same body** returns the
  original transaction. No second payment is created.
- Reusing the same key with a **different body** is rejected and does not create
  a payment (`422`). Bodies are compared by a hash over a canonical form, so key
  order and whitespace do not matter.
- A second request arriving with the same key while the first is **still in
  flight** returns `409`.
- A request that never completed — because the process died mid-flight — holds
  its key until a configurable lease expires, after which the key is reclaimable.

The race is resolved by a unique constraint in PostgreSQL rather than by
in-process locking, so the guarantee holds across processes. See
[ADR-0007](docs/decisions/adr-0007-idempotency-unique-constraint.md).

**Errors**

| Status | When                                                              |
| ------ | ----------------------------------------------------------------- |
| `400`  | Malformed JSON, unknown field in the body, missing/empty `Idempotency-Key` |
| `401`  | Missing or invalid credentials                                     |
| `409`  | Concurrent request with an in-flight idempotency key               |
| `422`  | Validation failure, or idempotency key reused with a different body |

### POST /v1/webhook-subscriptions

Registers the callback endpoint for the technical account.

**Request**

```json
{
  "url": "http://consumer:8080/internal/provider-events",
  "events": ["payment.approved", "payment.rejected", "payment.processing"]
}
```

**Response — `201 Created`**

```json
{
  "subscription_id": "sub_0199a0b7-1d55-7e6c-9a83-41f7d2b8e05c",
  "url": "http://consumer:8080/internal/provider-events",
  "events": ["payment.approved", "payment.rejected", "payment.processing"],
  "secret": "whsec_...",
  "created_at": "2026-08-10T12:00:00Z"
}
```

The `secret` is **shown exactly once**, in this response. It is stored
encrypted, under a key held separately from the database credentials, and is
never returned again. If it is lost, register a new subscription.

V1 allows one active subscription per technical account.

### POST /v1/webhook-deliveries/{delivery_id}/retry

Re-attempts a delivery that failed. Returns the delivery's updated state
(status, attempt count, last attempt time, last HTTP status).

## Webhooks

DummyPay emits `POST` requests with a JSON body to the subscribed URL:

```json
{
  "event_id": "evt_0199a1f4-4b17-70f2-a35d-8c1e64907bda",
  "type": "payment.approved",
  "created_at": "2026-08-10T12:00:00Z",
  "data": {
    "payment_id": "pay_0199a1f4-3c82-7d19-b4e6-2f8a91c05d3b",
    "reference_id": "checkout:123",
    "status": "APPROVED",
    "provider_transaction_id": "txn_0199a1f4-3c83-7a04-8f21-6d3b0e57c91a"
  }
}
```

Event types: `payment.approved`, `payment.rejected`, `payment.processing`.

**Signature.** Every request carries:

```
X-Webhook-Signature: <hex HMAC-SHA-256 of the raw request body, keyed with the subscription secret>
```

Verify against the **raw bytes** you received, before parsing. Re-serializing
the JSON will change the signature.

**Delivery lifecycle.** A delivery row is written *before* the HTTP call is
attempted, so nothing is ever sent without a record of it. Each delivery has:

| Field              | Meaning                              |
| ------------------ | ------------------------------------ |
| `status`           | `PENDING`, `SENT`, or `FAILED`       |
| `attempt_count`    | Number of attempts made              |
| `last_attempted_at`| Timestamp of the most recent attempt |
| `last_http_status` | HTTP status of the last attempt, if any |

A network failure or a non-2xx response leaves the delivery retryable. Retry it
via the endpoint above; a retry travels the same code path as the first attempt.

**Ordering is not guaranteed.** Deliveries are claimed from a work table by a
polling worker, so two events for the same payment may arrive out of order — a
`payment.approved` can reach your endpoint before the `payment.processing` that
preceded it. Consumers must tolerate this. It is a property of the design, not a
defect; see [ADR-0008](docs/decisions/adr-0008-outbox-in-process-worker.md).

## Configuration

Everything comes from the environment. There are no secrets in the repository
and no config files holding credentials.

| Variable                          | Required | Default | Purpose                                                      |
| ---------------------------------- | -------- | ------- | ------------------------------------------------------------ |
| `DUMMYPAY_HTTP_ADDR`                | no       | `:8080` | Listen address                                                |
| `DUMMYPAY_DATABASE_URL`             | yes      | —       | PostgreSQL DSN                                                |
| `DUMMYPAY_ACCOUNT_KEY_ID`           | yes      | —       | Basic auth username for the technical account                |
| `DUMMYPAY_ACCOUNT_KEY_SECRET`       | yes      | —       | Basic auth password for the technical account                |
| `DUMMYPAY_WEBHOOK_SECRET_ENC_KEY`   | yes      | —       | Key used to encrypt webhook secrets at rest — **separate from the database credentials**, base64, exactly 32 bytes decoded |
| `DUMMYPAY_PROCESSING_DELAY`         | no       | `3s`    | Settlement delay for `PROCESSING` scenarios; `0s` in tests    |
| `DUMMYPAY_IDEMPOTENCY_LEASE`        | no       | `30s`   | How long an in-flight idempotency key is held before it can be reclaimed |
| `DUMMYPAY_WORKER_POLL_INTERVAL`     | no       | `250ms` | How often the outbox worker checks for due work               |
| `DUMMYPAY_WEBHOOK_TIMEOUT`          | no       | `5s`    | Timeout for a single webhook delivery attempt                 |

Full validation rules are in [spec-v1.md §9](docs/spec-v1.md#9-configuration).
Copy [`.env.example`](.env.example) to `.env` and fill in real values — it is
gitignored, so nothing there ever reaches a commit.

## Running locally

What works today:

```sh
cp .env.example .env      # then edit the values you care about
docker compose up -d      # PostgreSQL
go run ./cmd/dummypay      # serves on :8080
curl http://localhost:8080/health
# {"status":"ok"}
```

`/v1/payments` and `/v1/webhook-subscriptions` are not implemented yet — see
the [roadmap](docs/plan-v1.md#roadmap). The service does not yet read
`DUMMYPAY_DATABASE_URL` or apply migrations; `/health` is the only route.

## Testing

The suite runs in two tiers. Domain and use-case tests use in-memory fakes and
need nothing running. Integration tests use a real PostgreSQL from
`docker compose`, each in its own schema — because idempotency and worker
claiming are database guarantees, and a fake would approve an implementation
that races in production. Without a database reachable they skip; in CI a skip
is a failure. See
[ADR-0013](docs/decisions/adr-0013-integration-tests-real-postgres.md).

The suite must pass with **no external network access**. Coverage targets:

- Approved payment
- Declined payment
- Both `PROCESSING` scenarios, including settlement
- Idempotent replay returning the original transaction
- Same key with a different body
- Concurrent requests with the same key returning `409`
- HMAC signature generation over the raw body
- Webhook delivery failure and successful retry

Run with:

```sh
go test ./...
```

## Scope

**In scope for V1:** sale (authorize + capture in one call), the four scenario
tokens, idempotency, webhook subscription, signed delivery with persistence and
retry.

**Out of scope:** tokenization, card storage, and real PCI compliance;
auth-only, pre-authorization, and later or partial capture; refunds,
chargebacks, 3DS, installments, anti-fraud, split payments, recurring billing,
Pix, and boleto; multi-account support, a dashboard, and a public API;
integration with any other service.

## Safety

DummyPay never receives, stores, or logs a PAN, CVV, expiry date, or any real
cardholder data. The API has no field for it. Payment outcomes are selected with
opaque scenario tokens only.

This is a test double. It processes no money and connects to no card network.
Do not put it in a production payment path.
