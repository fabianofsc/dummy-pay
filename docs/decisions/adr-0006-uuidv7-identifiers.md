# ADR-0006. Use UUIDv7 identifiers, prefixed at the API boundary

- **Status:** Accepted
- **Date:** 2026-08-10
- **Supersedes:** —
- **Superseded by:** —

## Context

Five public identifiers are generated by the service: `payment_id`,
`provider_transaction_id`, `subscription_id`, `event_id`, and `delivery_id`.
They are opaque to callers and must be stable for the life of the record.

One constraint is not obvious: the identifier must exist *before* the row is
written, because a payment and its outbox entry are inserted in the same
transaction and the entry references the payment
([ADR-0008](adr-0008-outbox-in-process-worker.md)). That rules out anything the
database assigns on insert.

The candidates were sequential integers, UUIDv4, UUIDv7, and ULID.

## Decision

UUIDv7 (RFC 9562), generated in the application, stored in native PostgreSQL
`uuid` columns.

At the HTTP boundary — and only there — identifiers are rendered with a type
prefix: `pay_`, `txn_`, `sub_`, `evt_`, `dlv_`. The prefix is presentation. It
is never stored and never part of the column value.

**Why not sequential integers.** They disclose volume, they are enumerable, and
they are assigned by the database at insert, which the transactional outbox
cannot accommodate.

**Why not UUIDv4.** Random keys scatter B-tree inserts across the whole index,
causing page splits and pushing the working set toward the size of the index
itself. `webhook_deliveries` is append-heavy and queried by time; random primary
keys are close to its worst case. UUIDv4 also carries no ordering, so any
time-ordered query needs a separate index.

**Why UUIDv7 rather than ULID.** These are technically near-equivalent: both are
128 bits with a millisecond timestamp in the high bits, so both give the same
insert locality and the same chronological sort. The tie is broken on
integration, not on merit — UUIDv7 is an IETF standard, PostgreSQL has a native
16-byte `uuid` type with native indexing, and `google/uuid` generates it. ULID
would need either a `char(26)` column or its raw bytes stuffed into a `uuid`
column with invalid version and variant nibbles. Neither is bad; neither is
better than using the type the database already has.

**Why prefix at all.** A prefixed identifier is self-describing in a log line,
and it makes it obvious when a delivery ID has been passed where a payment ID
belongs — a mistake that is otherwise invisible, since both are UUIDs.

## Consequences

**Positive**

- Time-ordered inserts keep index locality good as the delivery table grows.
- `ORDER BY id` is chronological, so investigating deliveries needs no extra
  index and no extra column.
- Native `uuid` columns: 16 bytes, no casting, no encoding decisions.
- Type confusion between identifier kinds is caught at the boundary instead of
  producing a mysterious 404.

**Negative**

- Long in logs and URLs. This is the concrete thing given up by not choosing
  ULID, and it is a daily, minor annoyance.
- Encode and decode logic at the boundary, plus tests for it.
- UUIDv7 embeds a creation timestamp, so an identifier discloses when its record
  was created. Acceptable for this service — there is no sensitive data to
  correlate it with — but it is a real property and would need reconsidering in
  a system where it is not.

## Compliance

A boundary test asserts that a well-formed UUID carrying the wrong prefix (for
example `dlv_` where `pay_` is expected) is rejected rather than silently
accepted. Storage and domain types are `uuid.UUID`, never `string`, so a
prefixed value cannot reach the database.

## Notes

Supersedes an earlier working choice of ULID made during stack discussion, which
was reversed before implementation in favour of the native column type. The
README examples were updated accordingly.
